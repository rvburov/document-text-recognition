Микробенчмарк сравнивает три способа точного поиска двух ближайших ORB-дескрипторов: скалярный POPCNT, экспериментальный AVX2 и исходный `BFMatcher` OpenCV. Оба индекса и оба расстояния должны совпадать. Производственная настройка `TemplateMatcher.UseAvx2` остается выключенной; измеритель выбирает режим явно и восстанавливает исходное значение при завершении.

Запускайте из корня репозитория с установленным SDK .NET, указанным в `global.json`. Сначала соберите проект:

```sh
dotnet build tools/MatchingPerformance -c Release
```

Для проверки результатов без замеров:

```sh
dotnet run --project tools/MatchingPerformance -c Release --no-build -- --samples docs/test-samples --quality-only
```

Короткий проверочный запуск использует два измерения каждого метода:

```sh
dotnet run --project tools/MatchingPerformance -c Release --no-build -- --samples docs/test-samples --repeats 2 --warmups 2 --native-threads 1 --label sanity --output artifacts/performance/matching-smoke.json
```

Основной запуск для измерений на Windows:

```sh
dotnet run --project tools/MatchingPerformance -c Release --no-build -- --samples docs/test-samples --repeats 6 --warmups 2 --native-threads 1 --require-avx2 --label windows-exact-hamming --output artifacts/performance/matching.json
```

`--repeats` задает положительное **четное** число измерений каждого метода для каждого варианта числа потоков. `--warmups 2` задает два прогрева. По умолчанию OpenCV получает один поток; для сравнения нескольких вариантов используйте `--native-threads "1,2,4"`. Метка `--label` описывает запуск и попадает в отчет.

`--require-avx2` требует экспериментальный API ядра и поддержку AVX2 процессором. Без них запуск завершается ошибкой, вместо замера скалярного запасного пути под именем AVX2. Без этого параметра старое ядро или неподдерживаемый процессор сравниваются только в режимах scalar/native; доступность и фактический скалярный запасной путь отражены в JSON.

До измерений программа один раз загружает три шаблона и отрисовывает четыре обязательных положительных PDF из набора. Для них строятся реальные ORB-дескрипторы: до 5000 признаков при длинной стороне 1600 точек. Каждый измеряемый проход обрабатывает все 12 пар «PDF — шаблон». Данные повторно используются без повторного рендеринга и поиска ORB.

Перед замерами проверяются **оба индекса и оба расстояния** ближайших соседей против `BFMatcher`: отдельно скалярный метод, AVX2 с готовым индексом и производственный переключатель без переданного индекса. Проверки включают равные расстояния, невыравненные ROI и шаг строк, пустые матрицы, единственный train-дескриптор, размеры train вокруг границ векторных блоков и запасной путь для 16-байтовых дескрипторов. При несовпадении результат нельзя использовать как подтверждение ускорения точного алгоритма.

AVX2 использует один заранее построенный неизменяемый индекс на шаблон, как кеш `PageFeatures` в производственном сопоставлении. Время подготовки, выделенные байты и размер каждого индекса записываются отдельно в `TrainPreparations`; они не входят в измерение повторного поиска. Это не скрывает подготовку индекса в сквозном прогоне: полный измеритель учитывает обычную загрузку шаблонов.

Измерения чередуются симметричными блоками ABCCBA, BCAACB, CABBAC (A=scalar, B=AVX2, C=native). Шесть повторов дают все три позиции каждому методу; без AVX2 используются ABBA/BAAB. Подготовка данных, рендеринг, ORB, вычисление SHA и проверки равенства исключены из измеряемого времени. Отчет содержит:

- время по часам и процессорное время процесса;
- выделения управляемой памяти и число сборок GC;
- результаты проверок точности;
- модель и производителя CPU по CPUID, доступность POPCNT и AVX2;
- ОС, версию .NET, сведения о нативной сборке OpenCV и числе потоков;
- SHA используемого ядра, входных файлов и дескрипторов, а также их количество.

В схеме JSON версии 2 `ComparedRowsByMethod` показывает полный объем проверки для каждого метода; `ComparedQueryRows` суммирует сравнения всех методов. Самые быстрые единичные измерения не используются как доказательство выигрыша: сравнивайте все повторения и средние/медианы.

Проводите замеры на свободном компьютере: закройте другие тесты, бенчмарки и задачи с заметной нагрузкой на CPU. Для повторного сравнения сохраняйте одинаковые входные файлы, число потоков, прогревы и повторы; сверяйте SHA и сведения об окружении в отчетах. Четыре vCPU на разных машинах могут иметь разную производительность: одного числа ядер для переноса результата на другой ПК недостаточно.

Этот запуск измеряет только сопоставление готовых дескрипторов. OCR и переименование файлов в него не входят. По полученным миллисекундам нельзя заявлять скорость обработки PDF, время пакета из 8000 документов или точность распознавания текста; для этого нужен отдельный сквозной замер с настоящими движками.

Windows workflow [`performance-hamming`](../../.github/workflows/performance-hamming.yml) после точной проверки выполняет четыре полных прогона по **500 PDF**: scalar, AVX2, AVX2, scalar. У всех одинаковые восемь обработчиков, ONNX-модели, известные строки и лимит OpenCV. Проверяются все имена и SHA-256 PDF, неизменность ядра, набора и моделей, запрошенный и фактический режим Hamming.

Для следующего полного прогона требуется среднее сокращение `WallSeconds` не меньше 5%, причем самый медленный AVX2 должен быть быстрее самого быстрого scalar. Это заранее выбранный практический критерий, а не утверждение статистической значимости. Если условие не выполнено, workflow сохраняет отказ в `selection.json` и не запускает 8000. Если выполнено, он обрабатывает **фактические 8000 PDF** с полной проверкой и отдельно записывает, уложился ли измеренный прогон в 20 минут. Время копирования корпуса, сборки и проверки хешей не выдается за время OCR, а прогноз из коротких партий не выдается за полный замер. Производственный флаг этим workflow не меняется.
