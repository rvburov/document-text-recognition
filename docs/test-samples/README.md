# Проверка редактора на созданных PDF

Здесь лежат созданные для проверки PDF со штампами и сохранёнными областями распознавания.
Это синтетические документы: таблица спецификации и демонстрационные чертежи с основной
надписью. Они проверяют работу программы на воспроизводимых примерах; чертежи и обозначения
не относятся к реальным изделиям и не являются производственной документацией.

## Проверить в программе

1. Скачайте папку `docs/test-samples` целиком.
2. В «Шаблоны» выберите вложенную папку **templates**. Вместе с каждым PDF должен лежать
   его файл `*.pdf.template.json`: там сохранены страница, назначения и координаты областей.
3. Откройте редактор шаблона. В PDF цветных линий нет — редактор покажет сохранённую разметку
   поверх страницы. Выберите поле, измените его границы, проверьте координаты и сохраните.
4. Кнопкой «Проверить скан» проверьте соответствующий PDF из папки **scans**. В результате
   видны фрагменты полей, отдельные ответы Tesseract/PaddleOCR и предполагаемое имя файла.
5. Для полного прогона скопируйте папку **scans** и выберите копию в «Обработка». Четыре
   положительных примера должны получить имена из таблицы. Пятый демонстрирует отказ при
   расхождении OCR; подробности ниже. Содержимое PDF при переименовании сохраняется.

| PDF | Шаблон и разметка | Ожидаемое имя |
|---|---|---|
| [01-specification-a4.pdf](scans/01-specification-a4.pdf) | Спецификация A4: синяя + зелёная; явно отмечено отсутствие типа | `ВКЕМ.461411.200 Модуль связи Спецификация.pdf` |
| [02-assembly-a4.pdf](scans/02-assembly-a4.pdf) | Основная надпись A4: синяя + зелёная + жёлтая | `ЮИЛГ.461411.123 Корпус Сборочный чертеж.pdf` |
| [03-schematic-a4.pdf](scans/03-schematic-a4.pdf) | Тот же шаблон A4; тип прочитан из документа | `ЮИЛГ.461411.124 Блок питания Схема электрическая.pdf` |
| [04-assembly-a3.pdf](scans/04-assembly-a3.pdf) | Основная надпись A3, альбомная: одна красная область | `ПРМД.301261.010 Рама сварная Сборочный чертеж.pdf` |
| [05-screenshot-like-specification.pdf](scans/05-screenshot-like-specification.pdf) | Пример по присланному изображению; проверка расхождения OCR | Только при подтверждении обоими движками: `АЦИЕ.202132.004 Э(Т)О МОЭА Спецификация.pdf`; иначе «Пропущен» |

PDF с типом «Схема электрическая» использует демонстрационную геометрию чертежа. В этом
примере проверяется чтение типа из штампа, а не условных обозначений электрической схемы.

Пятый PDF воссоздаёт обозначение и наименование с фотографии печатным шрифтом. На проверенном
образце 250 dpi Tesseract прочитал `Э(Т)О МОЭА`, а PaddleOCR — `Э(ТО МОЭА`, потеряв закрывающую
скобку. Области найдены и прочитаны, однако имя не подтверждено: файл пропускается с причиной.
Увеличение разрешения этого образца до 300 dpi также не дало подтверждённого результата
(низкая уверенность обозначения). Правила сверки для этих примеров не ослаблены. Этот тест
различает исправленное выделение областей и ограничения OCR конкретного текста. Он принимает
либо точный результат обоих движков, либо явный отказ; другое имя считается ошибкой.

## Непрерывный тест одного PDF: мышь → сохранение → OCR

`tests/App.Tests/TemplateEditorTests.cs` теперь проверяет всю последовательность в одном тесте:
создать PDF без рамок, открыть редактор, выделить поля действиями мыши, нажать «Сохранить шаблон»,
закрыть и открыть редактор, затем передать **этот же PDF** проверке распознавания. Проверка
заново загружает файл разметки с диска. Цветные области в PDF не встраиваются: сам PDF остается
прежним, координаты сохраняются в соседнем `.pdf.template.json`.

| Документ | Выделение мышью | Подтвержденный результат | Запись теста |
|---|---|---|---|
| Спецификация A4 | Синяя + зеленая | `АБВГ.466229.001 Плата Спецификация.pdf` | [Координаты и ответы OCR](editor-verification/Specification/verification.json) |
| Чертеж A4 | Синяя + зеленая + желтая | `ЮИЛГ.461411.123 Корпус Сборочный чертеж.pdf` | [Координаты и ответы OCR](editor-verification/Drawing/verification.json) |
| Чертеж A3 | Красная общая область | `ПРМД.301261.010 Рама сварная Сборочный чертеж.pdf` | [Координаты и ответы OCR](editor-verification/DrawingA3/verification.json) |

В каждом случае тест требует точного совпадения координат, полученных от мыши, сохраненных
на диске и использованных для OCR. Оба настоящих движка должны подтвердить ожидаемые поля;
контрольная сумма PDF до и после проверки совпадает. Для спецификации тип задан явной настройкой
отсутствующего поля, поэтому OCR читает только обозначение и наименование. На чертеже тип
читается из желтой или общей красной области.

Распознается изображение выбранной области: PDFium рисует фрагмент при 300 dpi, по совмещению
добавляется запас 1 мм, убираются линии граф и добавляются белые поля. Это не извлечение
текстового слоя всего PDF. `Bounds` в отчете содержит исходные сохраненные координаты в долях
страницы; для миллиметров X/ширину умножают на `PageWidth × 25.4 / 72`, Y/высоту — на
`PageHeight × 25.4 / 72`.

В GitHub Actions артефакт `tests-and-pdf-samples`, папка `editor`, содержит PDF именно этого
непрерывного теста, файлы разметки, OCR-фрагменты и JSON-отчеты. В репозитории выше сохранены
JSON-отчеты выполненной проверки. Другие PDF из `templates`/`scans` относятся к отдельному
набору образцов, описанному в начале этой страницы.

Для повторения:

```powershell
$env:DTR_EDITOR_TEST_OUTPUT = Join-Path (Get-Location) 'artifacts/editor-same-pdf'
dotnet test tests/App.Tests -c Release --filter FullyQualifiedName~Mouse_drawn_regions_are_saved_reopened_and_used_by_both_engines_on_same_pdf
Remove-Item Env:DTR_EDITOR_TEST_OUTPUT
```

## Записанный результат и повторение теста

[verification.json](verification.json) записывается самим тестом после проверки настоящими
Tesseract и PaddleOCR: четыре обязательных положительных примера и один пример с известным
расхождением. В нём указаны время и среда проверки, ожидаемые
и полученные имена, исходные ответы каждого движка, нормализованные поля и этапы проверки.
`Result: recognized` означает подтверждённое чтение; `Result: skipped` — отказ с причиной
в `Problem` и отсутствующим `ActualName`. Папка **crops** содержит изображения, переданные OCR.
Записанный прогон выполнен в Ubuntu 24.04.5 LTS с .NET 10.0.15 и Tesseract 5.3.4;
использован тот же дистрибутив Linux, что в проверках GitHub. Все пять тестов группы прошли:
четыре PDF распознаны точно, пятый проверен как отказ из-за расхождения в наименовании.

Тесты находятся в `tests/Core.Tests/Ocr/ManualTemplateOcrTests.cs`, генератор образцов —
`tests/Core.Tests/Samples/ManualTemplateSamples.cs`. Дополнительно проверяются поворот на
90°, наклон со сдвигом, выбор второй страницы шаблона, документ с обложкой, переименование
без изменения байтов PDF и повторный запуск со статусом «Имя уже верное».

Все проверки этой группы:

```powershell
dotnet test tests/Core.Tests -c Release --filter FullyQualifiedName~ManualTemplateOcrTests
```

Заново создать PDF и записанный результат (из корня репозитория, с установленными компонентами
OCR согласно `docs/pc.md`):

```powershell
$env:DTR_TEST_SAMPLES_OUTPUT = Join-Path (Get-Location) 'docs/test-samples'
dotnet test tests/Core.Tests -c Release --filter FullyQualifiedName~Saved_regions_read_specification_drawing_and_schematic_and_record_sample_pdfs
Remove-Item Env:DTR_TEST_SAMPLES_OUTPUT
```

На Linux:

```sh
DTR_TEST_SAMPLES_OUTPUT="$PWD/docs/test-samples" dotnet test tests/Core.Tests -c Release \
  --filter FullyQualifiedName~Saved_regions_read_specification_drawing_and_schematic_and_record_sample_pdfs
```

При обычном запуске тесты создают PDF во временной папке и удаляют их после проверки. Набор
примеров в репозитории обновляется только при явно заданной переменной `DTR_TEST_SAMPLES_OUTPUT`.
